# coding-guideline Design Doc

## Purpose

A story implemented with LLM assistance fails its requester in two ways that review keeps catching late: it drifts from the goal, and it becomes hard to change (the two roots are in guidelines.md, Two ways off the purpose). In one host project, nine autonomous laps produced 33 restated Business Rules and 8 tests whose fixtures held states production never holds. The development cycle had only a comment rule on the code side; nothing said how tests, code, and comments are derived from the input. This skill is that discipline: correspondence rules against the first root, and one method — Data-Oriented Programming — that turns the design's contract into records and operations and leaves the structure rules in the code, against the second.

## Design Decisions

| Decision | Rationale |
|----------|-----------|
| The purpose is the frame: the input is what was decided toward it, the rules are constraints, the means are the author's | A guideline read as "transcribe the design into code" lowers the author to a copier and produces a mechanical one-to-one mapping (one type per entry, one function per flow step) that serves the documents, not the purpose. Stating the freedom explicitly, and sending an input that works against the purpose back to the requester, keeps an LLM author at the purpose's altitude |
| Two roots, not one: the wrong source (code-anchored) and no structure | Folding both into "the output's shape was taken from the code" misnames the second: a faithful transcription of the input still piles rules in callers when nothing says where they go. Naming the roots separately is what lets the guideline stay at a few rules — each root requires its own antibody, and a defect is named by the rule it breaks instead of getting a rule of its own |
| Data-Oriented Programming is the method; each of its questions leaves one structure rule in the code, stated once, in that question's row (since 0.2.0, replacing 0.1.0's method-neutral rule table beside a default method) | With the method as the principle of thought, a rule is the invariant one answer leaves in the code, so each is stated once and the reviewer still judges by the rule, not by the author's means. Rejected: method-neutral rules beside the method, so that a reader who rejects the method still reads what must hold — read as the author, four of the six rules appeared twice, once abstract and once as the principle that produces them, and the route from the design to the code was split across four sections; a per-defect rulebook (never closes); the method alone (a reader cannot tell what it is for) |
| The method is Data-Oriented Programming v1.1 as Inside Java states it — four principles, verbatim — written in language-neutral terms | One named source keeps the method from drifting into the author's taste; v1.1 folds "validate at the boundary" into "make illegal states unrepresentable" and adds the separation of operations, which is the principle that produces homes. The host projects write Python while the source is Java, so the guideline uses terms both have (immutable record type, closed set of alternatives, pure function) and leaves per-language forms to the host |
| The route from the contract to the code is five questions the author answers from named input elements — the home, the record, the operation, the crossing, the rejected record — not a procedure; the home question comes first, searched by name and by location (since 0.2.0, replacing the single required step) | A stepwise order of work read as a transcription procedure and over-constrained the author. A question names what the author must settle from an input element and leaves the means, including the procedure inside a component, which the design documents also leave to the code: interfaces and data structures come from the Data Dictionary's contract, Business Rules become pure transformations under it, with side effects where they are needed. The home question is first because the two misjudgments it prevents — believing a home does not exist, and not noticing a sibling that already does the same — both come from writing before searching; searching by location covers a renamed term. The development cycle's observation gate is at lap scope; this one is per record and Business Rule, and the guideline does not assume the cycle is installed |
| The story's scope is read from the marks in the story's supplements, narrowed by the Boundary when the design is cut into several stories; the text is cited from the project's supplements (since 0.3.0) | The design skill merges a story's supplements into the project's before implementation and keeps the story's, marked, until its stories are done, and it copies in every project rule that binds the affected flow. Pinning every rule in the input would make each story re-pin the project's unchanged rules and another cut story's rules; the marks say which rules this story adds, changes, keeps, and retires. Rejected: every rule in the story's supplements — it re-pins rules already pinned where they live; the project's whole Business Rules — the same, wider |
| Existing code is a premise, not an input, and one rule covers code not in the method's form: the method shapes what the change creates; touched code is brought to it only as far as the change's purpose needs, never swept; the change still writes through one exit (since 0.2.0) | The code is changeable, so it cannot constrain the input; it is read to know the starting point. The guideline must hold on any codebase; a supplement per kind of legacy code would never close, one rule does. The one-exit limit keeps the antibody against the second root where it matters — the change's own effects — and a gap outside the change goes to the development cycle, otherwise every change grows into a sweep |
| Positive form is a clause of Business Rule beside its mechanism; failure judged by origin is the rule of the rejected-record question (since 0.2.0) | Both are properties of an operation at its boundary — what it acts on, what it does when a record is rejected — so each belongs to the question whose answer places that operation. A list of their own would be a second home for two rules |
| "Home" is the unit of the structure rules; "no structure" is the root | A home is the product of a structure — data and operations apart, one operation changing a record's state — so a record's home and a Business Rule's home coincide, and a Business Rule maps to the home's operation on its bound record in one line. Saying "behavior has no home" as the root names the symptom |
| A comment carries what only the author or the ticket knows; three typical kinds; two required references (Business Rule identifier, provisional origin); no restatement of a function's inputs and outputs | The earlier criterion, "a judgment with no home goes to a comment", sent too much to comments. The test is whether a reader of the committed code, tests, and design can reconstruct the intent; a ticket is not committed, so what lives only there needs a comment. A docstring that restates the signature doubles the function's home and doubles every change |
| References point from code to design only; the design skill never reads this guideline | Designs are judged in prose by the requester and must not bend toward one implementation method |
| No checklist and no review agent | The built-in code review cannot be replaced by a plugin; the development cycle hands the diff to it with the guideline's rules, and the reviewer's pass in SKILL.md points at the correspondence table, the method's table, Without a design, and Comments as the checklist. A separate checklist would be a second home for the rules; it is added only when a review path exists that reads a checklist and nothing else |
| Shipped as its own plugin, listed among the development cycle's default tools | Same shape as the design skill: the cycle names it as a default and reports when it is missing; projects without the cycle can still install it alone |

## Data Flow

Input (Design Doc, and the story's Data Dictionary and Business Rules read for the story's scope, the text cited from the project's supplements — or a ticket's purpose and success criteria, from which the author writes down the decisions the documents would have carried) → the author answers the method's questions in order: the home (one, none, several, or one not in the method's form) → the record (an immutable type from the Data Dictionary entry) → the operation (a pure function at the bound record's home, from each Business Rule in the story's scope) → the crossing (from the flow: check, then write at the exit) → the rejected record (failure by origin) → provisional values, their origin written in a comment → tests pinning one Business Rule in scope or criterion each; retired rules' code and tests removed → comments for the intent nothing committed says. Review branch: the diff is checked against the same requirements — the correspondence rules first, then the structure rules, the written decisions without a design, and the comments.

## Constraints & Tradeoffs

- The rules were derived from one host project's lap log (nine laps, 377 lines, 2026-09) and are verified against its defect classes. Whether an implementation written under the guideline avoids them is observed in later laps, by whether the same defect-class slugs recur in that log; as of 0.2.0 (2026-10) no lap has run under the guideline, and the table below is the evidence. The eighth class has no slug and is outside that check; it is seen only when a lap's judgment line names a failure's origin. The 0.2.0 restructure came from reading 0.1.0 as its author.
- The method is written for systems that pass records between components. A story with little record state gets the correspondence rules and the comment rule; the record and crossing questions have little to say.
- The home question counts hits; it does not decide what counts as the same record under a different name. That remains the author's judgment, informed by location.
- Delivery to an implementer agent (preload versus invoke at the writing stage) is decided by the development-cycle wiring, not here.

## Defect classes the rules cover

The eight classes observed in the host project's lap log, and the rule each breaks. Every class being derivable from the rules is the check the first release (0.1.0) was closed on, and 0.2.0 and 0.3.0 kept: each structure rule's label is one row of the method's table, and the correspondence rules changed only in scope (0.3.0).

| Defect class (lap-log slug) | Rule | Where it is stated |
|---|---|---|
| Record read or written outside its home (`data-homes-net-gaps`) | One truth, one point of change | The home question |
| Same answer derived in two places (`zero-cost-literal`, `stat-after-draw`) | One derivation | The record question |
| Business Rule text restated outside its home (`rule-duplication`) | Business Rules cited, not restated; Business Rule beside its mechanism | Correspondence rules; the operation question |
| Design term paraphrased in code (`term-single-meaning`) | Terms from the input | Correspondence rules |
| Partial key match on reuse (`reuse-without-identity-check`) | Identity as the input defines it | Correspondence rules |
| Persisted before validated, orphans left (`write-before-validate`, `partial-persistence-orphans`) | Check, then write | The crossing question |
| Fixture holding a state production never holds (`implementer-test-premise`) | Test premises from the record's definition | Correspondence rules |
| Failure handled without judging its origin (two judgment lines, no slug) | Failure judged by origin | The rejected-record question |
