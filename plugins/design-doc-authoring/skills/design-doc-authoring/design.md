# design-doc-authoring Design Doc

## Purpose

A story whose goal is vague, run with LLM assistance, gets its gaps filled from the code: the code is the most readable thing in reach, so judgments are made in its vocabulary and surface only after implementation, as review round-trips and rework concentrated on the one rule nobody had decided. Writing a design document does not by itself help — a document whose skeleton mirrors the code passes structural review and is still rejected, because its spine is the code, not the purpose. This skill makes the design a staged derivation from the purpose: the requester judges each stage in prose, undecided items are collected rather than filled in, one representative case is walked through before anything is cut into tickets, and the implementation receives only decided rules.

## Design Decisions

| Decision | Rationale |
|----------|-----------|
| Three documents: one Design Doc for judgment, two supplements (Data Dictionary, Business Rules) for the code side | Everything the requester judges must fit one reading; detail the walkthrough does not need pushes the whole picture out of view and inflates what an LLM session reads. The split test is a single question — can the walkthrough still run on the Design Doc alone — so the line does not depend on taste. A flat set of peer documents (system design, data contract, per-story design notes) was rejected: no single place holds the whole picture, and a story's implementation session reads on the order of a thousand lines |
| The chain checks (BR7, BR5, D7) test that the chain from purpose to means is closed within the documents, not only that each slot is filled; BR7 carries the business-rule definition itself — the intent connecting purpose and specification | A checklist that only asks whether an intent, grounds, or Essentials exist passes a document whose rules are specifications with an intent sentence attached, or rest on sections rather than decisions — the code-anchored shape the format exists to stop. Closure is judged by following references inside the documents, so an outside reader can judge it; whether the purpose is the right one stays with the requester. Rejected: slot-presence checks alone, found to pass that shape on a real design |
| The supplement list carries each supplement's location (a path from the project root) | Without a location the writer, the implementer, and a reviewer cannot find a supplement from the Design Doc — the same reason a Data Dictionary entry carries one. It also gives the review agent one discovery path. Rejected: fixed file names beside the Design Doc — projects with existing documents cannot always place them so |
| Write flow and rules, never procedure | Flow (records and keys passing between components) and rules (states a record must satisfy) are where contradictions appear; procedure (how a component works inside) in prose goes stale and is owned by code and tests. Observed in a host project: per-story design notes reached 150–300 lines each, and the bulk was procedure |
| Six judged stages, outside-in then by strength of constraint | The goal is judged from the user's side, so purpose and flow come first; records are harder to change than rules, so they are fixed before the rules that bind them. Judging per stage keeps a later stage from silently overturning an earlier judgment — it must reopen it as an undecided item |
| Undecided items go to one index with two options and a recommendation; implementation never fills them | The cost observed was not slow decisions but decisions that were never raised as questions: one undecided rule produced four review round-trips. A list the requester answers in one pass replaces scattered remarks. Items waiting on an observation are provisional, not undecided, so the index can actually empty |
| Walkthrough on the Design Doc alone, as a required stage | Contradictions do not show in a list of rules; they show when one case passes through. Needing a supplement to proceed is the signal that an essential is missing from the Design Doc |
| Business rule = the intent connecting purpose and specification; one sentence, one identifier, grounded in purpose/decision/fact, one home | The implementation cites a rule by identifier, so the sentence must carry the intent itself (no separate reason line to drift) and the grounds must lead back to a purpose (a rule grounded in another rule leads nowhere). This skill is the home of the definition; the development-cycle skill keeps the code-side handling (tests, comments) and points here |
| A story is designed against what exists — Facts names the project's supplements, the real code, or nothing — around its change but in the whole affected flow, with the project's entries and rules for that flow copied in and every item marked unchanged, changed, new, or retired | Observed in a host project: a design written as the delta alone left the requester unable to judge its flow until a whole-flow picture with the same marks was drawn, and the judgment that followed retired seven report kinds; its 25 rules, read against the project's 66, held four restatements and five changes or retirements of existing rules. The affected flow bounds the work because judging a large system's whole design is not feasible. The flow is marked against the real code when no supplements exist, since judging the flow needs the whole flow either way. Rejected: no marks without project supplements — the first design of a legacy system would fall back to the delta |
| A new record raises, at stage 3, which of the project's rules also bind it | A general rule (every record written atomically) bound a new record without naming it, and four design-doc-review passes over the story's documents did not surface it. Rejected: asking at the merge — the record's rules would stay undecided until just before implementation |
| One pair of project supplements, merged into before implementation with the requester auditing the difference; the story's supplements stay, read only, until the story closes | The merge in the host project found four overlaps and five contradictions among 28 rules, so it comes before implementation, where they can still be decided. The implementer needs the marks — which rules are new or changed, which retired ones take code and tests with them — so the story's supplements outlive the merge; read only, with any change going back through the design, so the project's stays the one home of the text. Rejected: deleting them at the merge — the implementer can no longer tell what the story changes; keeping them for good — two documents of one form, and a rule written into the story's makes two homes |
| References stay within the three documents; Facts names the project's supplements as what the design is set against, and the supplement list switches to them when the story's are deleted | Needing information outside the three documents contradicts the format's premise. Rejected: registering both pairs in the supplement list — it looks like two homes |
| Present tense only; history, verbatim quotes of decided items, and story order leave the document | A document that accumulates its own trail stops being judgeable in one pass; git log and the tracker already carry that trail. A verbatim quote stays only while its item is undecided, as the record of a pending judgment |
| Writing skill loads before drafting; filing skill takes over at close | Same shape as the sibling ticket-authoring skill: the writing model is drafting input, not a post-hoc check; cutting the design into tickets is the filing skill's domain |
| checklist.md: one binary check per rule in guidelines.md that the story's documents show before the merge, with IDs local to the checklist (S/D/DD/BR) | The design-doc-review agent's findings take the same shape as the sibling review agents' (docs-review, ticket-review), whose findings cite check IDs. A check ID is a label inside a finding, not a rule identifier that code cites. Rules still live only in guidelines.md: each check restates one rule as a binary question and adds none. Rules that act at or after the merge (the merge's grounds naming, the read-only window, the deletion) have no check, because the audit runs before them |

## Data Flow

Story ticket (purpose, provisional Done) → observed facts, the project's supplements among them → six stages, each judged by the requester, writing into Design Doc / Data Dictionary / Business Rules (for an existing system, copied items marked) → walkthrough → undecided index judged empty → audit → merge into the project's supplements, the requester auditing the difference → tickets cut by the filing skill; order and dependencies to the tracker → the story's supplements deleted when the story closes. Audit branch: Design Doc path → design-doc-review agent (supplements via the supplement list, checks from checklist.md) → read-only findings → the writer edits.

## Constraints & Tradeoffs

- Between the merge and the end of implementation, the project's supplements describe the system as designed, ahead of the code. Two stories merged against the same project supplements in that window see each other's changes only through the second merge's audit.

- The format was derived on, and tried against, systems that pass records between components (files, tracker rows, documents). A story with little record state has not been walked through it.
- The skill ships the review (checklist.md and the design-doc-review agent) but does not decide at which development stage a design task is inserted, or at which stage the review runs; those belong to the project's development-cycle wiring.
- Sorting a statement as flow / rule / procedure is a judgment, not a mechanical test; the examples in guidelines.md calibrate it but do not replace it.
